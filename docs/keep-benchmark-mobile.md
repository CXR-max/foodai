# 对标 Keep：手机端功能改造清单

> 盘点时间：2026-11-11　范围：`frontend/src`（手机端）+ `backend/app`
> 结论一句话：**我们已经有「吃」的完整闭环（识别 → AI 方案 → 打卡 → 积分 → 商城 → 成就），但「动」只停在一张手动填表；Keep 的护城河恰恰是运动记录 + 内容跟练 + 社区，这三块正是最该补的。**

---

## 一、现状盘点（手机端真实能力）

| 页面 | 路由 | 现在能做什么 | 手机端形态 |
|---|---|---|---|
| 识别 | `/recognition` | 拍照/选图 → 视觉模型认菜 → 本地营养库算营养 → 多菜校准 → 存饮食记录；带今日热量预算条、禁忌提示 | 重写过卡片列表，可用 |
| 方案 | `/plans` | 偏好勾选 + 多轮对话 → 约束求解逐天生成 → 可视化编辑 → 导入日历 | tab 切天，手机能看 |
| 打卡 | `/checkin` | 月历完成度 + 单日任务逐项打卡（+3）+ 手动运动表（类型/时长/强度，MET 估算）+ AI 点评 | **手动运动表单在页面最底部**，入口很深 |
| 仪表盘 | `/dashboard` | 今日摄入/消耗/连续打卡/排名 + 7/30 天热量 + 今日任务 + 快捷入口 + 分享海报 | 4 个数据块挤两行 |
| 我的 | `/profile` | 档案 + BMI + 体重曲线 + 人脸绑定 + 4 个二级入口 | 承担了「更多」职责 |
| 二级 | `/stats` `/mall` `/achievements` `/leaderboard` | 图表、兑换、徽章、积分榜 | 都是从「我的」进 |

**已有的能力底座（很扎实，别推翻）**
- 18 张表、营养库 13,423 条（活跃 1,847）、同义词/别名 5,276 条
- MET × 体重 × 时长 + 性别/年龄/体脂/体能的个性化消耗模型（`services/met.py`）
- 积分/成就/排行榜（Redis ZSet 降级 SQLite）、补签卡、分享海报
- LLM 抽象层（本地 Ollama / 云端 / Mock 三态可切）

**缺的（下面逐项展开）**
GPS 运动记录、轨迹地图、运动历史、课程/跟练、动作库、社区、关注/点赞/评论、挑战赛、步数/睡眠/饮水、食物库手动搜索、推送提醒、原生 App 能力。

## 二、Keep 的功能骨架（先看清结构，别只抄单个功能）

Keep 不是「一个跑步地图」，是四个引擎咬合：

1. **记录引擎** —— 跑步/骑行/行走（GPS 轨迹、配速、步频、心率）、训练完成记录、身体数据（体重体脂体围、饮水、睡眠、步数、经期）
2. **内容引擎** —— 课程库（瑜伽/力量/HIIT/拉伸/冥想）、动作库、训练计划、直播课、语音/节拍指导
3. **激励引擎** —— 连续打卡、等级/成长值、勋章、线上赛事、挑战赛、排行榜、组队
4. **关系引擎** —— 动态 feed、关注/粉丝、点赞评论、话题、圈子、运动达人

我们的现状：**记录引擎只有「吃」+ 手填运动；内容引擎只有「AI 生成餐单」；激励引擎齐全但只围绕「吃 + 打卡」；关系引擎为零。**

所以改造不是加一个地图页，而是把四个引擎都往「动」的方向接一遍。

## 四、P0：运动模块真实化（1–2 周，答辩必讲）

### 4.1 跑步/健走 GPS 记录 + 轨迹地图 ⭐核心

**为什么先做这个**：组长点的就是它；而且它一次性把「记录引擎」立起来，后面课程、挑战、社区全都能挂上去。

**入口**：底部新增「运动」tab → 运动首页大按钮「开始跑步」。

**页面拆成三个**

| 页面 | 内容 |
|---|---|
| `WorkoutView.vue` 运动首页 | 顶部本周数据（次数/里程/时长/消耗）；中间「开始跑步 / 开始行走 / 开始骑行」三选一；下方「训练课程」横滑；再下方运动记录列表（按周分组） |
| `RunTrackView.vue` 运动中 | 全屏地图 + 实时大数字（距离/时长/配速）+ 底部开始/暂停/结束 + 锁屏常亮 |
| `WorkoutDetailView.vue` 运动详情 | 轨迹回放（带起终点标记）+ 每公里分段配速条 + 消耗明细（复用 MET 弹窗那套「逐层系数」展示）+ 分享海报 |

**前端技术方案（Web 端可行）**

```
navigator.geolocation.watchPosition(enableHighAccuracy: true)
  → 点过滤：accuracy > 30m 丢弃；与上一点距离 < 5m 丢弃（防漂移）
  → 距离：haversine 累加；配速：滑动窗口（近 500m）
  → 暂停时不累计；切后台会掉点，用 WakeLock + 提示「请保持页面在前台」
地图：腾讯地图 JS API（或高德）加载 polyline，key 放 .env，别提交
```

**后端新增**

```python
# models/workout.py
class Workout(Base):
    id, user_id, sport_type      # run / walk / ride
    start_at, end_at, duration_sec
    distance_m, avg_pace_sec_km, calories, elevation_gain
    track        # Text，JSON: [{lat,lng,t,acc}]
    splits       # Text，JSON: 每公里配速
    source       # gps / course / manual
    plan_day_id  # 可空，关联方案任务
    note, created_at
```

```python
# routers/workouts.py
POST   /workouts               # 结束后一次性上传轨迹，后端重算距离/配速/消耗（不信任前端）
GET    /workouts?range=week    # 列表
GET    /workouts/{id}          # 详情（含 track）
DELETE /workouts/{id}
GET    /workouts/stats         # 本周/本月：次数、总里程、总时长、最佳配速
```

**验收标准**
- 手机浏览器授权定位后，走 200m 能画出连续轨迹，距离误差 < 5%
- 保存后自动出现在打卡页（当作当天运动已完成），积分/成就/排行同步
- 桌面端能看轨迹回放（答辩投屏用）

**已知坑（提前跟组长说清）**
- 定位必须 HTTPS 或 localhost，`npm run dev` 用 `--host` 给手机测要在同一局域网 + 自签证书，或者直接部署一版
- iOS Safari 切后台会中断，无法完全模拟原生；这点正好可以作为「后续要不要做小程序/App 壳」的论据

### 4.2 打卡页拆分（现在太重）

现状：`CheckInView.vue` 一个页面塞了月历 + 任务 + AI 点评 + 手动运动表 + 消耗弹窗，手机要滑半天。

改法：
- 手动运动表 **移出打卡页**，改成「运动记录页 → 手动补录」，打卡页只保留「今日任务 + 月历」
- 打卡页运动任务显示「来自 10:23 的跑步 · 3.2km」，点进去看轨迹
- 底部 tab 的 `tabbar` 从 5 个改成：**首页 / 运动 / 记录 / 社区 / 我的**

### 4.3 运动记录列表 + 累计统计（低成本高感知）

- 运动首页顶部四个数：本周里程、本周次数、累计里程、本月消耗
- 记录列表项：运动类型图标 + 日期 + 距离 + 时长 + 配速 + 一步到详情
- 复用现有 `StatsView` 的图表组件，加一张「周里程柱状图」

## 五、P1：内容化（2–4 周，把「动」做成可持续）

### 5.1 训练课程 + 跟练（不拍视频也能做）

Keep 的核心不是视频，是「**跟着计时器做完一组动作**」。我们零成本可做：

| 要素 | 做法 |
|---|---|
| 课程数据 | `courses` 表：标题、封面、难度、时长、预计消耗、标签（燃脂/塑形/拉伸/睡前）；`exercises` JSON：[{name, duration_sec, reps, tips, gif_url}] |
| 课程内容 | 先做 8–12 节：7 分钟晨间唤醒、10 分钟腹肌、15 分钟全身燃脂、8 分钟肩颈拉伸、睡前放松… 动作 GIF 用公开素材或自己拍 |
| 跟练页 | 大图动作 + 倒计时环 + 「下一个：开合跳 30 秒」+ 休息倒计时 + **Web Speech API 中文语音播报**（免费，`speechSynthesis`） |
| 结束 | 写入 `workouts(source=course)`，打卡 +3，发「今日训练完成」海报 |
| 课程列表 | 运动首页横滑卡片 + 分类筛选（手机端一屏 2 列） |

**这是性价比最高的一块**：没有视频，但交互完整度能到 Keep 的 70%，评委感知极强。

### 5.2 饮食记录补全（补齐「只能拍照」的短板）

- 食物库搜索：已有 1,847 条活跃池 + 别名 5,276 条，直接加 `GET /foods/search?q=`（按名称/别名/拼音首字母），选中后选份量 → 加记录
- 「常吃」快选：取该用户近 30 天高频菜，一键复制
- 「复制昨天」按钮
- 记录列表支持改份量/删（现在只有删）
- 餐次自动判断：按当前时间给默认餐次（11 点前早餐…）

### 5.3 身体数据扩展

新增日报表 `body_metrics(user_id, date, weight, water_ml, sleep_h, steps, waist_cm, body_fat)`：
- 饮水：首页一个「+250ml」水杯组件（点击有动画），最容易被用户每天用
- 睡眠/步数：手填或读 `DeviceMotion`（不精确，标注「估算」）
- 数据追踪页加「身体数据」分段：体重/体围/饮水/睡眠四张小图

### 5.4 每日目标与提醒

- 每日目标卡：热量摄入 / 运动消耗 / 饮水 / 步数 四个环
- 提醒：Web Notification + 站内红点（现在只有打卡红点），无后端成本

## 六、P2：社区与挑战（把「一个人用」变成「有人看」）

### 6.1 动态 feed（最小可用版）

```
posts(id, user_id, type, ref_id, content, images, like_count, comment_count, created_at)
post_likes(post_id, user_id)
post_comments(id, post_id, user_id, content, created_at)
follows(follower_id, followee_id)
```

- 发动态：一键把「运动记录」或「识别结果」生成动态（带图 + 数据卡）
- feed 页：关注 / 推荐两栏；卡片 = 头像 + 昵称 + 图文 + 点赞评论
- 手机端：底部 tab 「社区」，卡片式单列，双击点赞

### 6.2 挑战赛（自动结算，别做人工审核）

```
challenges(id, title, type, target_value, unit, start_date, end_date, reward_points, badge_code)
challenge_progress(id, challenge_id, user_id, current_value, completed_at)
```

- 类型：7 天累计跑 20km / 连续打卡 7 天 / 本周消耗 1500kcal
- 进度从 `workouts` 和 `check_ins` 自动汇总，达标自动发积分 + 徽章 + 站内信
- 首页横滑入口：「7 天跑步挑战 · 还差 6.2km」

### 6.3 排行榜改造（1 天工作量，感知很强）

现在只有「积分总榜」。加三个维度 tab：
- 本周里程榜（好友 / 全部）
- 本周消耗榜
- 连续打卡榜
Redis ZSet 已有，加 key 前缀即可；关键是**周榜要有「本周」概念**，别做成永久榜。

### 6.4 「好友」是社区的地基

没有好友，社区是空的。最低成本方案：邀请码 / 分享链接带 `?ref=`，互相加成好友；排行榜默认「好友榜」，否则全是陌生人。

## 七、手机端专项改动（这一块比加功能更影响观感）

### 7.1 导航重构（最重要的一条）

| 现在 | 建议 | 理由 |
|---|---|---|
| 识别 / 方案 / 打卡 / 仪表盘 / 我的 | **首页 / 运动 / 记录 / 社区 / 我的** | 对齐 Keep 心智；「方案」是低频，收进首页卡片；「打卡」并入首页 |

- 首页 = 仪表盘 + 今日四个环 + 待办 + 挑战入口（现在仪表盘的数据块太挤，改成 2×2 + 横向卡）
- 中间「记录」做成 **+** 号凸起按钮，点开弹「拍照识别 / 手动添加 / 记体重 / 记饮水」——这是 Keep 式的核心交互
- 「我的」保留二级入口：方案、数据追踪、商城、成就、排行

### 7.2 移动端组件替换（现在是桌面组件硬套）

| 位置 | 问题 | 改法 |
|---|---|---|
| 打卡页 `el-calendar` | 375px 下格子 52px，日期+完成度挤在一起 | 换成自绘月历网格（7 列 flex），或折叠成「本周横条 + 查看月历」 |
| 方案页 `el-table` | 手机端横向滚动体验差 | 换成餐次卡片列表（识别页已经做了 `dish-cards`，复用那套样式） |
| 各处 `el-dialog` | 全屏后关闭按钮在顶部，拇指够不到 | 统一改成底部抽屉 `el-drawer direction="btt"`，顶部留抓手 |
| `el-descriptions` | 手机端 2 列仍然挤 | 改 key-value 竖排列表 |
| `ElMessage` | 顶部飘一条，易被状态栏挡 | 换底部 toast 或自定义轻提示 |
| 所有按钮 | 部分小于 44px 点击区 | 统一最小高度 44px |

### 7.3 交互细节（用户说不出来但能感觉到）

- **下拉刷新**：首页、记录列表、动态 feed
- **骨架屏**：识别中、列表加载中（现在是 `v-loading` 遮罩，观感廉价）
- **页码/无限滚动**：识别历史已分页，运动记录和 feed 直接做触底加载
- **图片上传压缩**：拍照原图 3–8MB，上传慢还费 token；前端 canvas 压到长边 1280、质量 0.8 再传（识别精度基本不降）
- **拍照取景框**：现在是 `input file`，微信里会跳出系统选择器；建议 `getUserMedia` 做取景框 + 九宫格参考线 + 拍照后确认页（像 Keep 拍食物）
- **键盘遮挡**：对话输入框、体重输入框在 iOS 上会被键盘盖住，需 `scrollIntoView`
- **返回手势/页面转场**：路由切换加 150ms 左右滑入，消除「网页跳转感」
- **断网/超时**：统一错误提示 + 重试按钮，现在失败基本静默
- **PWA**：加 `manifest.json` + service worker，可「添加到主屏幕」全屏运行，离原生观感近一大步，成本 1 天

### 7.4 性能

- 路由已懒加载，但 Element Plus 全量引入（`main.ts`），首屏包体偏大 → 按需引入
- 图表 ECharts 全量引入 → 只引 `line/bar/pie` + 必要组件
- 首页 3 个接口串行（`getOverview` → `getFoodRecords` → `getCaloriesTrend`），改并行

## 八、不建议照抄的（会拖死进度）

| Keep 的功能 | 为什么不做 |
|---|---|
| 直播课 / 线下店 Keepland | 重运营，跟我们的 AI 定位无关 |
| 智能硬件（手环、体脂秤、跑步机） | 需要硬件和蓝牙协议，投入产出比极低 |
| 千万级食物库 | 现有 1,847 条够用，重点是搜索体验不是数量 |
| 视频课程拍摄 | 一部课要拍摄+剪辑+配字幕；用 GIF + 语音播报能到 70% 效果 |
| 心率/血氧监测 | Web 拿不到，必须原生 + 硬件，只能标「估算」 |
| 复杂的社交关系链（私信、群组） | 没有用户量时是纯负担，做到「关注 + 点赞 + 评论」就够 |

## 九、给组长的汇报口径（1 分钟）

> 我们现在的「吃」这条线是完整的：拍照识别 → AI 出方案 → 打卡 → 积分 → 商城 → 成就，数据和算法都比一般课设深。
> 但对标 Keep 缺的是「动」这条线：**Keep 的运动是「有轨迹、有记录、有内容、有对比」的，我们的运动只是一个手填表单**。
> 所以建议分三步补：
> 1. **P0（1–2 周）运动模块真实化**：GPS 跑步 + 轨迹地图 + 运动记录 + 独立运动 tab，把打卡从「手填」变成「自动同步」；
> 2. **P1（2–4 周）内容化**：课程跟练（计时器 + 语音，不拍视频）+ 食物库手动搜索 + 饮水/睡眠数据；
> 3. **P2（可选）社区与挑战**：动态 feed + 7 天挑战赛 + 本周里程榜。
> 同时手机端导航重构成「首页 / 运动 / 记录 / 社区 / 我的」，把桌面组件换成移动端卡片和抽屉——这块不加功能，但观感提升最大。

|---|---|
| A（前端-运动） | `WorkoutView` / `RunTrackView` / `WorkoutDetailView`，地图接入，轨迹绘制 |
| B（前端-改版） | 底部导航重构、打卡页拆分、移动端组件替换（table/calendar/dialog） |
| C（后端-运动） | `workout` 表 + 5 个接口、轨迹重算、与打卡/积分/成就打通 |
| D（后端-内容） | `courses` 表 + 课程数据、食物库搜索接口、`body_metrics` |

**统一约定**：所有新模块必须回写「积分 / 成就 / 排行榜」，否则又会变成和主体系平行的另一套数据，答辩时讲不圆。
