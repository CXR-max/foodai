# 运动板块 · 产品诊断与重构方案

> 诊断对象：`frontend/src/views/WorkoutView.vue`、`RunTrackView.vue`、`WorkoutDetailView.vue`、`components/TrackMap.vue`，以及 `backend/app/routers/workouts.py`、`services/workout_calc.py`
> 参考产品：Keep、Strava、Nike Run Club、Apple Fitness+、MyFitnessPal / 薄荷健康 / Noom、Garmin / Whoop、悦跑圈 / 咕咚、每日瑜伽 / 八段锦类
> 结论先行：**工程完成度不低，但定位错了。它现在更像"嵌在养生 App 里的 Keep 跑步页"，而不是"识膳智行"的运动板块。**

---

## 0. 一句话结论

你现在做的不是"运动记录"，是"跑步记录"。
跑步记录是全市场同质化最严重的能力，而你的产品真正的差异化资产是"吃"——中式食物库、拍照识别、养生方案、个性化 MET 消耗。运动板块没有把这条资产用起来，反而去和 Keep、Strava、悦跑圈拼它们最擅长、你最不擅长的那一屏。

**所以：不用推翻代码，但要换定位。** 从"记录你跑了多少"换成"根据你吃了什么，安排你今天怎么动"。

### 0.1 30 秒版

- **问题不是"做得糙"，是"做的东西不是这个产品最该做的"**：你复制了 Keep 最容易被替代的记录层，没复制它真正的留存引擎（课程/计划/社区）。
- **最该改的三件事**：首屏从"本周里程"换成"今日还能吃多少 + 下一件小事"；把"饭后走 + 跟练"做成主循环；把跑步降为进阶能力。
- **最该保留的**：轨迹过滤、服务端重算、地图降级、与打卡/积分的联动——这些是工程资产，不要推翻。
- **最该修的硬伤**：时长仍信前端、删除运动不回退消耗、跑步不算运动成就、方案里的瑜伽无法记录、补录不能选日期。
- **推荐路径**：答辩前做"3 天最小包"（换首屏 + 3 节跟练 + 报告对比 + 修 3 个 P0 + 改口径），答辩后走"吃动一体"两周版。

## 1. 先肯定：工程上你做对了什么

这几条比大多数课程项目扎实，重构时不要丢：

1. **链路是完整的**：选类型 → 记录 → 报告 → 历史 → 自动打卡，不是孤立的 Demo 页面。
2. **数据不轻信前端**：轨迹点过滤（精度 / 抖动 / 超速）、Haversine 累加、服务端重算，思路是对的。
3. **地图处理有取舍**：WGS-84 → GCJ-02 转换、瓦片失败降级网格、Canvas/Leaflet 自绘轨迹，答辩时是加分项。
4. **和主体系有挂钩**：保存运动自动写打卡、走原有积分规则，仪表盘/连续打卡能跟着动，这一点比"另起一套数据"强。

问题不在"做得糙"，在"做的东西不是这个产品最该做的"。

## 2. 五个根本问题（战略层）

### 2.1 对标错了层：你抄的是 Keep 的"记录"，Keep 的护城河是"内容 + 教练 + 社区"

Keep 2025 年的结构是：**5 个一级入口（首页 / 教练 / 运动 / 商城 / 我的）、4 万多节课程、AI 教练"卡卡"、社区、硬件、虚拟赛事**。2025 年 MAU 约 2177 万、订阅会员 274 万、营收 16.37 亿元，AI 教练卡卡已为 130 多万用户生成计划（数据见文末来源）。

它真正留住人的不是"跑步页"，而是：

- 打开首页就知道**今天练什么**（课程 / 计划）；
- 练的时候有**教练带**（语音、动作提示）；
- 练完有**社区和挑战**（点赞、排行、赛事）；
- 有**硬件和装备**闭环。

而"记录轨迹"这件事，Strava、Nike Run Club、悦跑圈、咕咚、华为运动健康、小米运动、Apple 全都在做，是行业基础设施，不是差异化。Strava 自己也在 2025 年连续收购 Runna（跑步训练计划）和 The Breakaway（骑行训练），从"记录工具"往"训练计划/教练"走——**连记录赛道的头部都在逃离纯记录**。

更值得警惕的是：Keep 的 AI 教练"卡卡"已经能做**拍照记饮食、饮食评价、生成计划、记体重**。也就是说，"Keep 不懂你吃了什么"这个假设正在失效。你的差异化不能停在"我们有拍照识别"，必须更深：**中式菜品/食材数据、养生与禁忌约束、吃动一体的能量账本**。

**所以：** 继续把跑步页打磨到 90 分，用户也不会因此选你；你缺的是"下一次打开的理由"。

### 2.2 用户选错了：跑步是低频高摩擦，你的用户是养生 / 亚健康 / 减脂新手

跑步的门槛：一双鞋、天气、场地、30 分钟、当天的动机。一周跑 2–3 次已经算不错。
而你的产品品牌是"识膳 · 知味 · 养生"，方案里默认运动是"快走 / 瑜伽 / 骑行"，用户画像并不是跑者。运动板块却把跑步放在 C 位、用配速和里程当主叙事，这和"养生"的品牌调性是冲突的。

高频、低摩擦、和"吃"天然绑定的运动是什么？

- **饭后走 10–15 分钟**：一天可以 3 次，不需要换衣服，和每一顿饭直接挂钩；
- **跟练**：八段锦、拉伸、肩颈、呼吸、睡前放松，8–15 分钟一节，每天都能做；
- **日常活动**：久坐起身、爬楼、通勤步行。

餐后散步对餐后血糖的改善有明确研究支持（三餐后各走 15 分钟 vs 一次 45 分钟连续走，见文末 PubMed）。"饭后百步走"又是中文语境里现成的文化认知。**这比"5 公里跑"更适合你的用户，也更容易每天发生。**

你的模块里其实有"快走"，但它只是跑步的降级版：同样的 GPS、同样的配速、同样的报告，没有把"饭后走"当成核心产品。

### 2.3 没有"下一次"：报告是终点，不是起点

现在的闭环是：**跑 → 看报告 → +2 分 → 结束**。
Keep 的闭环是：**计划/课程 → 练 → 记录 → 分析 → 下一课**。
Strava 的闭环是：**记录 → 路段/PR/kudos → 下次再来**。
Apple 的闭环是：**三个环没闭合 → 今天再动一点**。

你的产品里，AI 方案其实**每天都有运动任务**（`planner.py` 默认按"快走 / 瑜伽 / 骑行"轮换，20–60 分钟，还带预计消耗），但运动首页**完全不读它**；`workouts.plan_day_id` 字段留了，前端从来没传。用户今天该练什么，系统明明知道，却没告诉他。

更具体的断裂：成就系统里的"活力满满"只统计 `task_key == "manual_exercise"` 的打卡，而跑步写入的是 `task_key == "workout"`——**跑 10 次也解锁不了运动徽章**。

### 2.4 两本账：Workout 和 CheckIn 各存一份消耗

保存一条运动时，后端同时写 `workouts` 和 `check_ins`，两份都存 `calories`。
但读的时候：仪表盘、周报、数据追踪读 `check_ins`；运动页读 `workouts`。这就是两份账。

已经出现的具体问题：

- 删除一条跑步记录时，只有它自动生成的 `task_key == "workout"` 打卡会被删；如果它完成的是方案里的运动任务（`task_key == "exercise"`），打卡行会保留，**仪表盘的"今日消耗"不会回退**。
- 打卡页底部仍然保留"手动运动打卡"表单，运动页也有"跑步机/跳绳补录"——**同一件事两个入口**，用户不知道用哪个，也可能重复记。
- 方案任务被运动记录"顺手完成"时，打卡行里的消耗会改用运动记录的重算值，和打卡页原来的口径不再一致。

这正是你们文档里警告过的"手环一套、跑步一套、打卡一套，三份数据打架"，只是现在缩小成了两套。

### 2.5 Web GPS 是演示能力，不是产品能力

浏览器里：切后台/锁屏就断、必须 HTTPS、iOS Safari 会杀页面、城市高楼区漂移、拿不到海拔/步频/连续心率、没有后台续记。你们已经做了 WakeLock、退出拦截、错误提示，这些都对，但改变不了平台限制。

把 GPS 跑步当**主入口和门面**，等于把产品建在最不可靠的能力上。它应该降级为"进阶功能"，门面换成"随时可做、不依赖定位的小运动"。

## 3. 市面上最好的产品到底怎么做

### 3.1 一张表看清结构

| 产品 | 它真正卖什么 | 运动在体系里的位置 | 最值得学的一条 | 不要照抄 |
|---|---|---|---|---|
| **Keep** | 内容 + AI 教练 + 社区 + 硬件 | 一级入口，但首页回答"今天练什么" | 课程/计划驱动留存；教练降低门槛 | 跑步页本身 |
| **Strava** | 社交 + 路段 + 训练 | 记录是入口，订阅卖训练计划 | 记录之后的比较（segment / PR / kudos）；隐私区 | 社交关系链（没用户量时是负担） |
| **Nike Run Club** | 语音教练 | 跑步即产品 | 戴着耳机就能跑，不用看屏幕 | 明星教练、大制作 |
| **Apple Fitness+** | 闭环 + 课程 + 手表 | 圆环是每日习惯 | 一个环，每天闭合 | 硬件 |
| **MyFitnessPal / 薄荷 / Noom** | 饮食日记 / 行为改变 | **运动只是日记里调整预算的一行** | 净卡路里、剩余预算、餐后联动 | 百万级食物库 |
| **Garmin / Whoop** | 训练负荷 / 恢复 | 数据回答"今天该不该练" | readiness / 恢复评分 | 专业指标堆砌 |
| **悦跑圈 / 咕咚** | 赛事 / 奖牌 / 跑团 | 目标驱动参与 | 线上挑战、奖牌 | 线下赛事运营 |
| **每日瑜伽 / 八段锦类** | 低门槛跟练 | 课程即产品 | 8–15 分钟一节，每天可做 | 长视频课程 |

### 3.2 三种范式，你选错了

1. **记录工具**（Strava、Garmin）：卖"我跑了多少"。同质化，靠社交、硬件、训练负荷差异化。
2. **内容平台**（Keep、Peloton、Apple Fitness+）：卖"今天练什么"。课程、教练、计划是引擎。
3. **行为改变**（Noom、MyFitnessPal、薄荷、Duolingo）：卖"每天做一点"。触发器、低摩擦、反馈、连续。

**你的产品基因是第 3 种，不是第 1 种。** 现在的运动模块是"第 1 种的半成品"：有记录，没有比较；有报告，没有下一步；有积分，没有习惯。

### 3.3 如果只学一条

> 每个留存好的产品，都有一个"下一次打开的理由"：Keep 是明天的课，Strava 是朋友的 kudos 和 PR，Apple 是没闭合的环，Duolingo 是连续天数。
>
> **你现在没有这个理由。** 跑完一次和跑完十次，产品给用户的反馈是一样的。

## 5. 用户实际使用时，会在哪里卡住

| # | 阶段 | 用户期望 | 现在发生什么 | 后果 |
|---|---|---|---|---|
| 1 | 第一次进"运动" | 告诉我今天该干什么 | 本周 0.00km，三个运动按钮 | 不知道点哪个，退出 |

## 6. 换方案可以吗？可以，而且建议换"定位"，不是推翻代码

### 6.1 三个选项

| 方案 | 做什么 | 成本 | 风险 | 答辩效果 | 产品效果 |
|---|---|---|---|---|---|
| **A. 换叙事（保底）** | 保留三页；首页改成"今日能量账本 + 今天动什么"；加 3 节跟练；报告加对比/分享；修 P0；口径改成"不做第二个 Keep" | 3–5 天 | 低 | ++ | + |
| **B. 换核心循环（推荐方向）** | 以"饭后走 + 跟练"为核心；GPS 跑步降为进阶；课程播放器；周目标/连续；吃动联动；两本账合并 | 2 周 | 中 | +++ | +++ |
| **C. 换品类（彻底）** | 砍掉 GPS/地图，只做"吃动一体"的日常活动与跟练 | 4 周+ | 高 | ? | ++++ |
| **D. 砍掉运动** | 删除 tab，只保留打卡里的手动记录 | 1 天 | 低 | - | - |

### 6.2 建议

- **现在做 A，答辩后走 B。** 不要选 C（时间不够、丢掉已完成的工程资产），也不要选 D（"动"是你和纯饮食 App 的差异点）。
- 如果答辩就在 1 周内：A 的"3 天最小包"（见 8.2）足够把故事讲圆，且不用大改代码。
- 如果还有 2–3 周：直接按 B 做，把"饭后走 + 跟练"做成主循环，跑步保留为进阶。

## 7. 推荐方案 B：从"跑步工具"改成"吃动一体的能量账本"

### 7.1 一句话定位

> **Keep 记录你跑了多少；我们回答你今天该怎么动——基于你刚吃的那顿饭。**

对外一句话：**"不是第二个 Keep，是第一个把吃和动算成一本账的 App。"**

### 7.2 首页重做（最重要的一屏）

现在的首屏是"本周里程 + 三个运动类型"，这是**记录工具**的首屏。
应该换成**行为改变**的首屏：

```
┌────────────────────────────────┐
│ 今天还能吃 560 kcal             │
│ 摄入 1450 · 消耗 210 · 目标 1800 │
│ ▓▓▓▓▓▓▓▓░░░░ 81%               │
├────────────────────────────────┤
│ 下一件小事                      │
│ 午餐 620 kcal，20 分钟后        │
│ 快走 15 分钟 ≈ 70 kcal          │
│ [ 开始 15 分钟 ]                │
├────────────────────────────────┤
│ 饭后走   跟练   进阶跑步         │
├────────────────────────────────┤
│ 本周活动 92 / 150 分钟          │
│ 连续 4 天 · 还差 58 分钟         │
└────────────────────────────────┘
```

要点：

- **第一屏回答"我现在该做什么"**，不是"我过去跑了多少"。
- "下一件小事"的触发来自：今天哪顿饭、摄入了多少、现在几点、今天是否已动、方案里今天是什么运动。
- 三个入口按**摩擦从低到高**排：饭后走 → 跟练 → 进阶跑步。跑步不再站 C 位。
- 周目标用**活动分钟数**（WHO 建议每周 150 分钟中等强度），而不是里程——走路、跟练、跑步都能计入。

### 7.3 内容：8–12 节跟练（不需要拍视频）

Keep 课程的核心不是视频，是"**跟着计时器和口令做完一组动作**"。零成本可做：

| 课程 | 时长 | 场景 | 消耗（60kg 估算） |
|---|---|---|---|
| 饭后 10 分钟快走 | 10 min | 午餐/晚餐后 | ~35 kcal |
| 饭后 15 分钟快走 | 15 min | 晚餐后 | ~55 kcal |
| 八段锦 · 双手托天 | 8 min | 晨起/久坐后 | ~30 kcal |
| 肩颈放松 | 6 min | 办公间隙 | ~15 kcal |
| 睡前拉伸 | 10 min | 睡前 | ~25 kcal |
| 腹式呼吸 | 5 min | 压力大/睡前 | ~10 kcal |
| 晨间唤醒 | 7 min | 起床后 | ~30 kcal |
| 久坐起身 | 5 min | 每小时 | ~15 kcal |
| 靠墙静蹲 | 4 min | 居家 | ~25 kcal |
| 低强度有氧 | 12 min | 任意 | ~70 kcal |

每节只需要：动作数组（名称/时长/口令/注意）、计时器、语音播报（`speechSynthesis`）、消耗预估。**1–2 天就能做出播放器，感知极强。**

### 7.4 播放器

- 大计时环 + 当前动作名 + "下一个：开合跳 30 秒" + 休息倒计时
- 语音口令 + 可选背景节奏
- 暂停 / 跳过 / 提前结束
- 结束直接生成报告，写入 `workouts(source='course')`，自动完成当天运动任务

### 7.5 报告：从"数据堆"改成"一句人话"

```
这次 15 分钟快走，消耗 78 kcal
≈ 半碗米饭（100g）

比上次多走了 6 分钟
本周第 4 次 · 连续 3 天
餐后 30 分钟内完成 ✓
```

再往下才是：轨迹/分段/消耗推导/数据来源。
加三个动作：**对比（vs 上次/月均）、PB 标记、分享海报**。没有心率就整块隐藏。

### 7.6 吃动联动（你唯一能打赢 Keep 的地方）

| 时机 | 动作 |
|---|---|
| 识别保存一餐后 | "这顿 620 kcal，20 分钟后走 15 分钟？" 一键开始 |
| 运动结束后 | "消耗 78 kcal；今天蛋白质还差 20g，晚餐可以加个鸡蛋/豆腐"（按目标，不做奖励式文案） |
| 仪表盘 | 今日"净摄入 = 摄入 − 消耗"；7 天净摄入趋势 |
| 周报 | 活动分钟数、餐后走次数、达标天数，而不是只报"消耗 kcal" |
| 方案 | 今天的运动从 `plan_day.exercise` 直接读，一键开始，完成后回写 |

### 7.7 数据模型：合并成一本账

- **`workouts` 是运动唯一账本**；`check_ins` 只存"任务状态 + 关联 id"，不再单独存消耗（或保留字段但统计不读）。
- 统计口径：以 `workouts` 为主，`sum(workouts.calories)` 加上"没有被任何 workout 关联"的手动打卡消耗（按 `workouts.checkin_id` 反查去重），避免重复计算。
- 新增**运动目录**（code / 名称 / 是否有 GPS / 计量单位 / MET / 图标），替代中文字符串枚举。
- 新增 `exercise_goals`（周活动分钟、周次数）、`exercise_sessions`（课程进度，或复用 `workouts(source='course')` + `course_id`）。
- 类型目录至少覆盖：跑步、快走、骑行、跑步机、跳绳、瑜伽、拉伸、八段锦、呼吸、其他。

### 7.8 导航：从 6 个 tab 回到 5 个

推荐：**首页 / 记录 / ＋ / 方案 / 我的**

- "＋"：拍照识餐 / 开始运动 / 补录 / 记体重 / 记饮水
- 运动收进"记录"（按饮食/运动筛选）和首页卡片
- 打卡页删除手动运动表单，只显示"今日运动：来自 18:32 的跑步 4.65 km →"
- 如果答辩必须保留独立 tab：改名"动一动"，内容是"今日卡片 + 跟练 + 历史"，不要再用"本周里程"当首屏

### 7.9 可信与隐私

- 有轨迹时，时长/距离/配速全部从 `track` 推；前端只做展示
- 轨迹抽稀到 600–800 点再存（Douglas-Peucker），别把 1 小时 3600 点原样塞 SQLite
- 精度徽章 + "GPS 信号弱，距离可能偏差"提示；允许手动校正并留痕
- 隐私区：分享/公开视图隐藏起终点各 300–500m；默认私密
- 导出 GPX / 删除全部数据

## 9. 答辩口径改写

### 9.1 不要再说

| ❌ 现在 | 为什么危险 |
|---|---|
| "我们按 Keep 的逻辑补成一条完整链路" | 评委第一反应：那你和 Keep 差在哪？ |
| "Keep 有的四格数据我们都有" | 把评价标准交给对手，越比越像仿制品 |
| "底部从 5 个 tab 变成 6 个" | 6 个 tab 是减分项，不是功能点 |
| "心率字段已预留" | 听众只听到"没做" |

### 9.2 改成

> "我们不做第二个 Keep。Keep 记录你跑了多少，我们回答你今天该怎么动——基于你刚吃的那顿饭。
> 跑步只是进阶能力；日常是饭后走 10 分钟、八段锦 8 分钟、睡前拉伸 10 分钟。
> 我们的差异不在轨迹，在中式饮食数据 + 养生约束 + 吃动一体的能量账本。"

### 9.3 Q&A 预案

| 问题 | 回答 |
|---|---|
| 为什么不做视频课程？ | 课程核心是计时 + 口令 + 动作提示，不是视频；我们用 8 分钟八段锦/拉伸验证了跟练闭环，成本不到拍视频的 1/10。 |
| 为什么跑步不是核心？ | 跑步是进阶；我们的用户是养生/减脂人群，不是跑者。让他们每天动 10 分钟，比一周跑一次 5 公里更有价值。 |
| 和 Keep 差在哪？ | Keep 有内容、社区、硬件，我们不追；我们的差异是中式饮食数据、养生约束、吃动一体的能量账本。 |
| 数据准不准？ | GPS 有误差，我们做了过滤、服务端重算、隐私区；日常走路用计时/计步，不依赖 GPS。 |
| 为什么只有这几个运动？ | 类型不是越多越好，是"采集规则"不同。我们先覆盖最高频的走路/跟练，跑步/骑行作为进阶。 |

## 10. 不要做

1. **不要补社区、直播、硬件、连续心率**——没有用户量时是纯负担，且打不过 Keep。
2. **不要做全类型运动**——先把"饭后走 + 跟练"做透。
3. **不要做实时上传/后台定位**——Web 做不到，投入产出比为负。
4. **不要为了"像 Keep"保留 6 个 tab**——导航是产品观点，不是功能清单。
5. **不要用 emoji 当正式图标**——可以后换，但答辩前至少统一一套线性图标。
