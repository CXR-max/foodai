# 人脸登录 · 汇报备忘

> 用途：明天汇报时的讲稿、预判提问、演示动线与风险预案。
> 所有数字均来自本机实测（2026-11-04，`backend/scripts/check_baidu_face.py`）。

---

## 0. 一句话定位

**人脸登录做的是「1:1 人脸比对」——验证"你这个人"是不是"这个账号的主人"，不是从人堆里认人（1:N 检索）。**

---

## 1. 先澄清一个关键点（容易被问倒）

| | 用在哪 | 是什么 |
|---|---|---|
| **人脸比对** | 登录验证 | 百度人脸对比 V3，**专用卷积神经网络（CV）**，不是大模型 |
| **智谱 GLM-4-flash / GLM-4.6v** | 食物识别、方案生成 | 大语言模型 / 多模态大模型 |

**这两套是完全独立的。** 如果汇报时把"人脸"说成"用了大模型"，评委追问一句"用的哪个模型、多少参数、怎么微调的"就答不上来了。正确说法是：人脸走的是成熟的商用 CV 接口，大模型用在识别和方案生成环节。

---

## 2. 技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 采集 | Vue 3 + `getUserMedia` + Canvas | 720 宽请求、640 宽落盘、JPEG 0.8 |
| 动作检测 | Canvas 帧差（96×72 探针） | 判断"镜头前有人在动"，非真活体 |
| 接口层 | FastAPI + SQLAlchemy + Pydantic | 5 个 REST 接口 |
| 比对 | 百度智能云「人脸对比 V3」 | `aip.baidubce.com/rest/2.0/face/v3/match` |
| 鉴权 | JWT 双票据（ticket → token） | HS256，ticket 120s 一次性，token 7 天 |
| 存储 | SQLite + 本地目录 `backend/data/faces/` | 底库照片不进静态资源目录 |

---

## 3. 实现链路（五步）

```
① 输入用户名  → POST /auth/face/status      查这个账号绑没绑脸
② 唤起摄像头  → 端上动作检测（3 次画面变化）  确认是活人在镜头前
③ 拍照上传    → POST /auth/face/verify      服务端 1:1 比对
④ 比对通过    → 返回 ticket（120s / 一次性）
⑤ 兑换凭证    → POST /auth/face/login       ticket 换 JWT
```

| 环节 | 文件 |
|---|---|
| 采集弹窗、动作检测、压缩 | `frontend/src/components/FaceCaptureDialog.vue` |
| 前端接口封装 | `frontend/src/api/face.ts` |
| 5 个路由（status/me/enroll/verify/login） | `backend/app/routers/face.py` |
| Provider 抽象 + 百度实现 | `backend/app/services/face/provider.py` |
| 一次性票据 | `backend/app/core/security.py` |
| 底库元数据表 | `backend/app/models/user_face.py` |
| 连通性自检脚本 | `backend/scripts/check_baidu_face.py` |

## 4. 六个设计决策（讲这部分最显专业）

1. **Provider 抽象（策略模式）**
   `compare(ref, cap)` 一个接口，`mock` / `baidu` 两个实现。切环境只改 `.env` 一行，业务代码零改动；将来私有化，加一个 `InsightFaceProvider` 即可。

2. **双票据，比对通过不直接发 token**
   避免"一次比对成功 → 拿到 7 天凭证"。ticket 120 秒过期、用一次即废（内存表 `pop`），被截获也换不出东西。

3. **底库隔离**
   照片存 `backend/data/faces/{user_id}.jpg`，**不在** `/uploads` 静态目录里，前端拿不到 URL。

4. **登录禁上传**
   登录弹窗不渲染"上传照片"入口，只走实时摄像头；上传仅限已登录的绑定场景。否则拿张照片就能登录。

5. **防枚举 + 限流**
   按用户名 60 秒 5 次；"用户不存在"和"没绑人脸"返回同一句提示，不区分。

6. **底库照与现场照参数不同**
   底库照 `liveness_control=NONE`（静态照片，开活体会误判），现场照 `LOW`（拦翻拍）。这个细节说明真的调过。

## 5. 为什么用云，不用本地开源

| 维度 | 百度人脸对比 V3 | InsightFace / ArcFace | face_recognition (dlib) |
|---|---|---|---|
| 比对准确率 | 商用级 | 论文级高，但要自己选模型调阈值 | 老模型，弱于前两者 |
| **活体防翻拍** | **自带静默活体** | 无，需另配 anti-spoofing | 无 |
| 部署 | 零部署，HTTP 调用 | 装 onnxruntime/torch + 100~300MB 模型 | 需编译 dlib，Windows 很麻烦 |
| 推理速度 | 云端，不占本机 | CPU 约 100~300ms/次 | 更慢 |
| 维护 | 官方迭代 | 阈值、质量、异常全自己扛 | 同上 |
| 隐私 | 照片出内网 | **全本地，更优** | 全本地 |
| 离线 | 不可用 | 可用 | 可用 |
| 成本 | 免费 1000 次/月，超出按量 | 免费但吃服务器 | 免费 |

**结论（诚实的版本）：** 本地方案在隐私、离线、边际成本上更优；云方案在**活体能力、准确率稳定性、零运维**上更优。当前选云的理由是——没有 GPU、团队没有 CV 调参经验、月调用量远低于免费额度、演示在即不能把时间花在编译 dlib 上。**架构上留了后路**：Provider 抽象，切本地只加一个类。

## 6. 三分钟逐字稿

> 语速放慢，每段之间停半秒。

"我负责的是登录模块里的人脸登录。

先明确它解决什么问题。它不是'从一堆人里认出你是谁'，而是'验证你这个人，是不是这个账号的主人'——技术上叫 **1:1 人脸比对**。

整个流程五步。第一步，用户在登录页输入用户名，前端先问后端这个账号绑没绑过脸；第二步，唤起摄像头，画面里有个椭圆框，用户把脸放进去，前端做一次动作检测，确认镜头前是个活人；第三步，拍一张照片，压到 640 宽，连同用户名发给后端；第四步，后端从底库取出这个账号当初绑的照片，两张一起交给**百度人脸对比接口**，返回一个 0 到 100 的相似度，我们把阈值定在 80；第五步，通过之后**不直接发登录凭证**，先发一张 120 秒、只能用一次的 ticket，前端拿 ticket 再换正式 token。

选型上，人脸比对用的是百度智能云的人脸对比 V3。这里要说清楚一点：**它不是一个'大模型'**，而是专门做人脸的卷积神经网络，把两张脸各提取成一个特征向量，再算相似度。项目里真正的大模型是智谱 GLM，用在前面的食物识别和方案生成，跟人脸是两套东西。

为什么不用本地开源的？三个原因。一是**活体**，开源方案基本只管'这两张脸像不像'，防翻拍、防屏幕要自己再搭一套，百度这边自带静默活体；二是我这台机器**没有 GPU**，本地跑 ArcFace 一次两三百毫秒，还得装运行时、下载模型，明天就要演示，时间不该花在这上面；三是**调用量**，一个月一千次免费额度，我们完全够用。

但我没有把路堵死：比对逻辑抽了一个 Provider 接口，mock 和百度是两个实现，将来要私有化，加一个 InsightFace 的实现类就行，业务代码一行不用改。

安全上做了四件事：底库照片存在后端本地目录，不在静态资源目录里，前端拿不到；登录场景禁止上传照片，只能实拍；比对通过只给 ticket 不给 token；按用户名限流。"

## 7. 一分钟版

"人脸登录做的是 1:1 比对，用来验证'你是不是这个账号的主人'。前端 `getUserMedia` 采脸、做动作检测、压到 640 宽上传；后端取底库照片，调百度人脸对比 V3 拿 0~100 的相似度，阈值 80；通过后先发一张 120 秒一次性的 ticket，再换正式 JWT。用云不用本地开源，是因为它自带静默活体、我们没 GPU 也没时间调 CV 模型；但比对层做了 Provider 抽象，要私有化改一个类就行。"

## 8. 高频追问 · 八条

**Q1：你用了什么大模型做人脸识别？**
A：人脸这块没用大模型。用的是百度人脸对比 V3，专用的人脸卷积网络，输出是相似度分数不是文本。项目里的大模型是智谱 GLM，用在食物识别和方案生成。两者是独立的模块。

**Q2：准确率多少？**
A：实测同一个人两张不同照片是 96 分，同一张自比 100 分，阈值 80。但我要说明——**我只做了小样本验证，没有跑过大规模评测集**，所以不能给你一个"准确率 99%"的数字。工程上真正要定阈值，需要一批真/假样本对来画 ROC。

**Q3：能防住拿照片攻击吗？**
A：分层看。端上有动作检测，只放行实时摄像头，登录页不让上传；云端的现场照开了 `liveness_control=LOW`，能挡一部分翻拍。但这两层都不是金融级活体——**真正的活体需要接百度人脸核身的 H5 SDK，由服务端验签**。这是我知道的下一步。

**Q4：为什么阈值是 80？**
A：百度官方 1:1 的推荐档，80 分以上判同人。它是个误识率和拒识率的权衡点：调高更安全但本人也可能被拒，调低反之。我们现在取的是通行值，还没用真实样本校准过。

**Q5：百度挂了或者断网怎么办？**
A：`verify` 捕获不到结果会返回 502，前端提示"人脸服务暂时不可用，请改用密码登录"。人脸是**增强手段不是唯一入口**，密码登录始终可用。

**Q6：人脸数据合规吗？**
A：底库照片存在服务器本地目录，不入静态资源、不进版本库，支持用户自己解绑并删除文件，传输走 HTTPS。**还差一项：绑定时应该有一个"单独同意"的勾选**，因为人脸属于敏感个人信息，个保法要求单独同意——这块是我还没补的。

**Q7：1000 次/月够用吗？**
A：课程演示和个人使用完全够。真上生产，要么买 QPS 包（约 270 元/月/QPS），要么私有化部署。

**Q8：能多台服务器部署吗？**
A：现在 ticket 存在单进程内存里，多 worker 会取不到，需要换成 Redis。我在代码注释里标了这个限制。单机演示没问题。

## 10. 风险预案

| 风险 | 表现 | 预案 |
|---|---|---|
| 现场网络差 | 比对超时（15s）后 502 | 提前预热（先跑一次自检），并准备录屏 |
| 摄像头权限被拒 | 弹窗提示"权限被拒绝" | 提前在浏览器里授权；用 Chrome 演示 |
| 免费额度用完 | 百度返回 18 / 限额错误 | 提前查控制台剩余次数 |
| 光线太暗识别不过 | "人脸不匹配" | 换到窗边，或把阈值临时调到 70 应急 |
| 底库照质量差 | 本人反复被拒 | 提前重新绑定一次，确保底库是清晰的正面照 |

**兜底开关**：万一云端完全不可用，把 `backend/.env` 的 `FACE_PROVIDER` 改成 `mock` 并重启后端，可以继续演示流程（但页面会显示"演示模式"，**不要在现场主动提这个开关**）。
