# 转 App 前的改造流程（待确认版 · 不改代码）

> 前置约束：现状是浏览器手机端（Vue3 + Element Plus），已接小米手环但**只是手动导入**，组员本地有脚本、仓库里没有；后续确定要打包成 App；组长要求"打包后不能再改"。
> 本文只做流程与影响面梳理，供你检查，**不含任何代码改动**。

---

## 一、先把"打包后不能改"这句话说清楚

**技术上：能改。操作上：确实很麻烦。** 她说的不是全错，但结论过于绝对，而这句话正好会误导你们的改造顺序。

| 情况 | 真能改吗 | 实际代价 |
|---|---|---|
| 后端接口、算法、数据 | ✅ 随时改 | 无。App 里调的是同一个后端 |
| 前端页面/样式 | ⚠️ 要重新打包 | 改完 `npm run build` → 重新打 apk → 重新安装。不能像网页那样刷新就生效 |
| 原生权限/插件（定位、蓝牙、通知） | ❌ 必须重新打包 | 改 `AndroidManifest.xml` / `Info.plist`，属于原生壳层，Web 代码改不了 |
| 已装到别人手机上的旧版 | ❌ 不会自动更新 | 除非做热更新（安卓可行，iOS 不允许改核心功能） |
| 上架应用商店的版本 | ❌ 要重新审核 | 审核周期按天/周算 |

**所以"不能改"的准确说法是：打包之后，每次改界面都要重新出一版安装包并重新分发。**
而这恰恰意味着：**你现在做的每一个数据模型决策，在打包后都会变成"改一次就要重装一次"的成本。**

一句话结论：**功能可以后加，数据结构不能后改。** 所以顺序必须是「先把数据结构和能力接口定死 → 再做功能 → 最后打包」，而不是先把页面堆完。

---

## 二、打包方式决定了改造量（这条必须先问清楚）

| 方案 | 现有 Vue 代码改动 | 能拿到的原生能力 | 适合我们吗 |
|---|---|---|---|
| **Capacitor 套壳**（推荐） | 几乎为零，`dist/` 直接塞进去 | 定位（含后台）、相机、通知、蓝牙、文件 | ✅ 最省事，Vue3 直接可用 |
| uni-app 重写 | 全部重写 | 全 | ❌ 等于重做项目 |
| Flutter / 原生 WebView 壳 | 需要一个壳工程 + 少量桥接 | 全（但要自己写桥） | 次选，工作量大 |
| 微信小程序 | 全部重写（且不能用 Element Plus） | 定位、支付、无后台定位 | 只在"要分享给同学用"时才值得 |

**建议问组长的第一句话**：我们是 Capacitor 套壳还是原生重写？如果她没想过，就按 Capacitor 准备——因为它对现有代码最友好，而且**能拿到浏览器拿不到的后台定位和手环直连**，正好补上我们最大的短板。

## 三、现在必须做的三件"地基"事（打包后改最痛，所以现在改）

### 3.1 能力抽象层：页面不直接调浏览器 API

现在的问题是：一旦页面里直接写 `navigator.geolocation`，打包成 App 后要么不能用（拿不到后台定位），要么得逐页改。

所以要提前收口成一个"平台适配层"，页面只调它：

| 能力 | Web 实现（现在） | App 实现（打包后） | 页面要不要改 |
|---|---|---|---|
| 定位轨迹 | `navigator.geolocation` | `@capacitor/geolocation`（可后台） | **不改** |
| 手环/健康数据 | 手动导入文件 | 小米 SDK / Health Connect 直连 | **不改** |
| 拍照 | `<input type=file capture>` | `@capacitor/camera` | **不改** |
| 通知提醒 | Web Notification | `@capacitor/local-notifications` | **不改** |
| 文件导出 | Blob 下载 | `@capacitor/filesystem` | **不改** |

落地就是新增一个目录 `frontend/src/platform/`，里面三个文件：`index.ts`（对外统一接口）、`web.ts`（浏览器实现）、`native.ts`（App 实现，打包时启用）。**这是转 App 唯一必须提前做的架构动作。**

顺带一个真实风险：`main.ts` 里 Element Plus 是全量引入，`echarts` 也是全量，App 首屏会更慢（WebView 没有浏览器缓存优势），打包前一并处理。

### 3.2 数据模型：一张 workouts 表装四种来源

**这是全篇最重要的一条。** 现在手环数据是独立的脚本，运动是打卡页里的一个表单，两边不互通。如果继续这样，打包后你会发现：手环数据是一套、App 记录是另一套、打卡又是一套，三份数据打架，改一次要动三处。

正确做法是**一张表 + 一个来源字段**：

```
workouts
  id, user_id, sport_type            # run / walk / ride / indoor_run ...
  source                             # gps / band / manual / course
  start_at, end_at, duration_sec
  distance_m, avg_pace_sec_km, calories
  avg_hr, max_hr, hr_series(JSON)    # 手环能给，GPS 给不了
  track(JSON)                        # 只有 gps 有，手环没有
  splits(JSON)                       # 每公里分段
  external_id                        # 手环记录的唯一 id，用于幂等
  import_id                          # 来自哪次导入，便于回滚
  plan_day_id                        # 关联方案任务（可空）
```

```
body_metrics（日汇总，一天一行）
  user_id, date, steps, sleep_min, deep_min, rem_min,
  resting_hr, water_ml, weight_kg, source
  unique(user_id, date)
```

```
data_imports（导入批次，出问题能回滚）
  id, user_id, source, filename, row_count, ok_count, skip_count,
  status, created_at, raw_path
```

### 3.3 打包当天一定会踩的三个坑（现在就能提前修）

| 坑 | 现状 | 后果 |
|---|---|---|
| **CORS 白名单** | 只允许 `localhost:5173` | App 里的 origin 是 `capacitor://localhost` / `http://localhost`，**所有请求会被浏览器内核直接拦掉**，App 打开就是一片空白 |
| **接口地址** | `http.ts` 已支持 `VITE_API_BASE` + `assetUrl`（这个口子留得对） | 打包前必须把后端部署到公网 HTTPS；App 里没有 Vite 代理 |
| **明文 HTTP** | 现在是 `http://` | Android 9+ 默认禁止明文请求，必须上 HTTPS，否则打包后接口全挂 |

CORS 和 HTTPS 这两条，**打包当天才发现的话，会让你以为"打包失败"，实际是网络层拒了**。建议现在就把 CORS 改成读配置（允许 capacitor/localhost 和你的内网 IP）。

## 四、手环数据整合流程（组员代码合并）

### 4.1 先认清手环能给什么、不能给什么

| 数据 | 手环有没有 | 用途 |
|---|---|---|
| 步数 | ✅ | `body_metrics.steps`，做每日目标环 |
| 连续心率 | ✅ | 回填 workouts 的 `hr_series`，画心率区间（Keep 的核心图表之一） |
| 静息心率 | ✅ | 健康趋势卡 |
| 睡眠（深/浅/REM） | ✅ | `body_metrics`，睡前/睡眠评分 |
| 运动消耗 | ✅ | 只作交叉校验，别直接覆盖我们的 MET 计算 |
| 运动记录（类型/时长/心率） | ✅ | `workouts(source='band')` |
| **GPS 轨迹 / 配速 / 海拔** | ❌ **没有** | 必须靠手机定位补，两者是互补不是替代 |

**这一点要跟组长讲明白**：手环数据不能替代 Keep 的跑步地图——手环只记"你动了多久、心率多少"，不记"你在哪跑的"。所以对标的重点仍然是"手机定位记录轨迹 + 手环提供心率"，两条数据合并才是完整的一条运动记录。

### 4.2 整合分四步（不要直接把组员的脚本搬进来）

1. **定统一格式**：约定一份 CSV/JSON schema（时间、类型、时长、距离、心率、消耗），让组员把他脚本的输出**转成这个格式**，而不是我们兼容他的格式。要一份**样本文件**，先看真实字段长什么样。
2. **建 imports 表 + 导入接口**：`POST /integrations/import`，上传文件 → 解析 → 落库 → 返回"成功 N 条 / 跳过 M 条 / 失败原因"。**必须幂等**（同一份文件重复上传不产生重复记录），靠 `(user_id, source, external_id)` 去重。
3. **前端加"数据导入"页**：选文件 → 预览前 10 行 → 确认导入 → 结果报告。**不要做成"小米手环专用页"**，做成通用的"导入健康数据"，否则以后换设备又要加一页。
4. **合并逻辑**（精髓）：如果某天导入的手环记录和 App 记录的跑步**时间重叠**，提示"要把这段心率合并到这次跑步吗？"——合并后一条记录既有轨迹又有心率，这才是 Keep 级别的数据完整度。

### 4.3 组员代码的风险要先确认

- 他的脚本是**直接写数据库**还是调接口？直接写库的话，导入表结构一变就崩，必须改成走接口。
- 他的解析逻辑有没有做**去重**？重复导入会不会把步数翻倍？
- 他的字段口径和我们对不对得上（消耗是"活动消耗"还是"总消耗"）？

这三条不确认，合并后会出现"数据看着有，但统计全错"。

## 五、对标 Keep 的改造顺序（按约束重排，不按功能好看程度排）

| 阶段 | 内容 | 改动文件 | 工期 | 为什么排在这 |
|---|---|---|---|---|
| **S0 地基** | 平台适配层 + workouts/body_metrics/data_imports 三张表 + CORS/HTTPS | `src/platform/*`、`models/*`、`alembic/versions/*`、`main.py` | 3~5 天 | 打包后改数据模型最痛 |
| **S1 手环导入** | 统一 schema + 导入接口 + 导入页 + 合并逻辑 | `routers/integrations.py`、`views/ImportDataView.vue` | 3~4 天 | 组员代码必须先进主流程，否则永远孤儿 |
| **S2 运动模块** | 运动 tab、跑步页（GPS）、报告页、历史、周月统计、打卡联动 | `views/Workout*`、`routers/workouts.py` | 1~1.5 周 | 对标 Keep 的可见主体 |
| **S3 内容跟练** | 课程表 + 跟练计时器 + 语音播报 + 完成打卡 | `views/Course*`、`routers/courses.py` | 1 周 | 让"动"能持续，不依赖出门 |
| **S4 界面移动化** | 底部导航重构、日历/表格/弹窗换移动端形态、骨架屏、下拉刷新 | `MobileTabBar.vue`、`CheckInView.vue` 等 | 穿插 3~5 天 | 放最后，因为页面还会增删 |

**顺序不能倒的原因**：S2 的跑步页要用 S0 的定位适配层，S2 的报告页要显示 S1 导进来的心率；如果先做页面，等数据模型一改，页面全要返工——这正是"打包后不能改"真正想避免的事。

## 六、打包前冻结清单（拿去给组长勾）

- [ ] 应用名 / 图标 / 启动页 / 包名（`com.xxx.foodai`）
- [ ] 权限文案：定位（前台 / "始终允许"）、相机、通知、蓝牙、健康数据读取
- [ ] 后端已部署到**公网 HTTPS**，App 内没有代理
- [ ] `CORS` 放行 `capacitor://localhost`、`http://localhost` 和测试机 IP
- [ ] `VITE_API_BASE` 在打包环境里指向线上地址（不要留 `/api`）
- [ ] 版本号规则 + 后续重新打包的分工人
- [ ] 首屏白屏兜底（网络差时给 loading/重试，不能裸白）
- [ ] 数据导出 / 账号注销入口（合规，也是答辩加分项）
- [ ] 至少一台真机（安卓）完整跑一遍：登录 → 识别 → 跑步 → 报告 → 打卡

## 七、打包后仍然能改的事（可以拿去安抚组长）

- 后端任何接口、算法、提示词、数据：**随时改，App 不用动**
- 前端界面：能改，只是要重新出一版安装包（版本号 +1，重新分发/重装）
- 新增功能页：同上，前提是**数据表没变**——这就是 S0 必须先做的原因
- 唯一真不能改的：已经装到别人手机上的旧版本不会自动变成新版（除非做热更新，iOS 不允许）

---

## 八、需要你确认的 5 个决策点

1. **打包方式**：Capacitor 套壳 / 原生重写 / 小程序？（决定 S0 的适配层怎么写）
2. **打包时间点**：还剩几轮迭代？如果只剩两周，S3/S4 要砍。
3. **打包后能不能重新打包**：如果能，"冻结"其实是"版本管理"，我们可以继续迭代；如果不能，就要在打包前把 S0~S2 全做完。
4. **手环数据的样本文件**：能不能拿到一份真实导出文件？字段对不上，S1 就得返工。
5. **心率是否必须做**：涉及设备与隐私；如果不做，报告页就只画配速和海拔，少一块 Keep 有的图。

## 九、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 组员脚本直接写库 | 表结构一改就崩 | S1 强制走接口 + 幂等 |
| 打包当天才发现 CORS/HTTPS 不通 | App 白屏，误判为打包失败 | S0 提前改 CORS，先部署一版 HTTPS 测 |
| 手环数据没有轨迹 | 以为"接了手环就有地图" | 明确：轨迹靠手机定位，手环只给心率 |
| 浏览器后台定位被限流 | 跑步切后台断轨迹 | 页面上注明"保持前台"，App 版换原生插件解决 |
| 导航一次改太多 | 中途没法用，演示翻车 | S4 放最后，改之前保留旧菜单入口 |
