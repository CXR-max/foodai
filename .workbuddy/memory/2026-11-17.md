- 生产构建后首屏约 300KB gzip（dev 模式 2~3MB），局域网秒开
- 启动：`npm run preview -- --host ::`（双栈，同时监听 IPv4/IPv6）

- 截图校验脚本：`frontend/scripts/verify.cjs`（统计高德瓦片 200 数量，确认底图真的加载）

## 2026-11-18 融合后修复（组员代码合入）

### 计划生成失败的 5 个真因（都不是"模型没接"）
1. `plan_intent.py` 用 `settings.intent_model` / `LLM_INTENT_TIMEOUT` / `LLM_INTENT_MAX_TOKENS`，`config.py` 全缺 → AttributeError 500（已补字段 + intent_model property）
2. 营养库 foods 0 条：`food_seed.py` 要 `name_zh`/`category_l1`，而 `app/data/foods_seed.json` 是旧格式 `name`/`category` → KeyError，`_food_values` 已做双格式兼容，导入 1850 条
3. 繁简转换依赖 `opencc` 未装：繁体菜名（萊姆/中脂鮮羊乳）`normalize_name` 后仍繁体，查不到自己 → 复核退回 `category_average_diet(None)` 全库均值 → 番石榴 200g 算成 340 kcal（实际 76）→ 复核永远"营养越界"
   - 修法：`foods_data._build_indexes` 增 `_raw_name_map`（按原始 name），`match_entry` 第一顺位查它，不依赖 opencc
4. 份量只能整份（`common_portion_g` 多为 100/200g）→ 热量粒度 150~250 kcal，落不进 2390 上限 → 求解器无解
   - 修法：`planner.SERVING_STEPS = 2`（支持半份），建模/输出/`_day_nutrients` 三处同步换算
5. 求解太慢：`SOLVER_TIME_LIMIT 3.0 → 0.8`，last_resort 8.0 → 4.0；3 天方案 172s → 57s
